# Claude Code 사용법 (이 프로젝트 한정)

`CLAUDE.md`가 규칙이라면, 이 문서는 **실제로 뭐라고 입력할지**의 모음이다.

## 시작

```bash
cd C:\my-projects\one-line-capture
claude
```

Claude Code는 세션이 시작될 때 `CLAUDE.md`를 자동으로 읽는다.
`docs/` 안의 세 문서는 자동으로 읽지 않으므로, 첫 프롬프트에서 읽으라고 지시한다.

---

## 프롬프트 원칙 4가지

1. **T번호로 지시한다.** "로그인 만들어줘"가 아니라 "T1.4를 진행해줘".
   범위가 문서에 이미 적혀 있어서 엉뚱한 데로 새지 않는다.
2. **한 번에 하나.** "T1.4랑 T1.5 해줘"라고 하면 커밋이 뭉치고 어디서 틀렸는지 못 찾는다.
3. **끝나면 학습 노트 3줄을 확인한다.** 이해가 안 되는 줄이 있으면 거기서 멈추고 물어본다.
   이 프로젝트에서 가장 중요한 습관이다.
4. **막히면 에러 전문을 붙여넣는다.** 요약하지 말고 그대로. 스택트레이스에 답이 들어 있다.

---

## 첫 세션 프롬프트

```
docs/spec.md, docs/stack.md, docs/tasks.md를 먼저 읽어줘.
읽고 나서 T1.1을 진행해줘.

T1.1 = 프로젝트 초기화:
- 디렉터리 구조 (api/, web/, docs/) 생성
- Java + Node용 .gitignore (.env 반드시 포함)
- README.md 스켈레톤 (제목, 한 문장 소개, 로컬 실행법 자리만)
- git init 후 첫 커밋까지

끝나면 멈추고 학습 노트 3줄을 남겨줘.
```

## 이후 태스크

```
T1.2를 진행해줘. 끝나면 멈추고 보고해줘.
```

이 한 줄이면 된다. 나머지는 `CLAUDE.md`와 `docs/tasks.md`에 다 있다.

---

## 상황별 프롬프트

**설명을 듣고 싶을 때 (코드 수정 없이)**

```
방금 만든 @MapsId 매핑이 왜 필요한지 설명만 해줘. 코드는 건드리지 마.
```

**에러가 났을 때**

```
docker compose up 했더니 이 에러가 났어. 원인이 뭔지 먼저 설명하고,
고치기 전에 어떻게 고칠 건지 말해줘.

<에러 전문 붙여넣기>
```

**결과가 마음에 안 들 때**

```
지금 구현이 CLAUDE.md의 "절대 하지 말 것"에 걸리는 것 같은데 확인해줘.
```

**주차 마무리 점검**

```
docs/tasks.md의 1주차 데모 조건을 지금 코드가 만족하는지 직접 실행해서 확인해줘.
안 되는 게 있으면 목록으로 알려주고, 고치기 전에 멈춰.
```

## 주의할 점

- **Claude Code가 스코프를 늘리려 하면 거절한다.** "이왕이면 카테고리 기능도"는 v2다.
  `spec.md` §6을 근거로 대면 된다.
- **`git diff`를 눈으로 본다.** 최소한 커밋 전에 한 번. 전부 맡기더라도 이건 직접 한다.
  안 보면 4주 뒤 레포에 뭐가 들었는지 모르게 된다.
- **`docker compose up`은 직접 친다.** 배포가 이번 프로젝트의 학습 목표(30%)다.
  이것까지 대신 시키면 배우려던 걸 안 배우게 된다.
- **파서 테스트는 케이스를 직접 추가해본다.** 최소 5개. 자기가 쓰는 말투로.
  `저녁 12000원`, `내일까지 리포트`, `담주 화욜 스터디` 같은 것.

# tasks.md — 4주 작업 목록

> 최종 수정: 2026-08-25
> 단위: 1태스크 = 2~3시간 (= 한 번 앉아서 끝낼 수 있는 크기)
> 총 34태스크 / 약 90시간 → **주당 약 22시간**

**먼저 솔직하게:** 주 22시간은 학기 중 학생에게 빡빡하다. 이 일정은 "여유 있는 계획"이 아니라
**"전부 다 하면 이만큼 걸린다"는 정직한 견적**이다. 그래서 §막히면 잘라낼 순서가 이 문서에 있다.
일정이 밀리는 건 실패가 아니라 예정된 일이고, 그때 **기간을 늘리지 말고 범위를 줄인다.**
5주, 6주가 되어도 완성하면 성공이다. 다만 v1 범위는 절대 늘리지 않는다.

## 이 문서 쓰는 법

- 한 태스크를 시작하면 **그것만** 한다. 중간에 다른 게 눈에 띄면 §부록 "나중에 목록"에 적고 돌아온다.
- 태스크가 3시간을 넘어가면 **끝내지 말고 쪼갠다.** 쪼개지는 게 실패가 아니라 정상이다.
- 각 주차 끝에 **"이번 주 데모"** 가 있다. 데모가 안 되면 다음 주로 넘어가지 않는다.
- 커밋은 태스크 단위로. 커밋 메시지에 태스크 번호를 넣으면 나중에 흐름이 보인다 (`T2.3 금액 파싱 룰 추가`).

## 1주차 — 뼈대와 저장

**이번 주 목표:** `curl`로 한 줄 던지면 MySQL에 행이 하나 생긴다.
**이번 주 데모:** `docker compose up` → `curl -X POST .../captures -d '{"text":"테스트"}'` → DB에 저장 확인

| # | 작업 | 예상 | 완료 기준 |
|---|---|---|---|
| **T1.1** | GitHub public 레포 생성, `.gitignore`(Java+Node), README 스켈레톤, MIT 라이선스 | 2h | 레포에 첫 커밋이 올라가 있다 |
| **T1.2** | Spring Boot 3 + Java 21 프로젝트 생성(start.spring.io: Web, JPA, MySQL Driver, Flyway, Validation), `GET /api/v1/health` 구현 | 2h | 로컬에서 `curl localhost:8080/api/v1/health` → `{"status":"UP"}` |
| **T1.3** | `docker-compose.yml`에 MySQL 8 서비스 추가 (utf8mb4, named volume, healthcheck), 앱은 아직 로컬 실행으로 접속 | 3h | `docker compose up db` 후 앱이 DB에 붙고 Flyway가 뜬다 |
| **T1.4** | Flyway 마이그레이션 `V1__create_capture.sql` 작성, 앱 기동 시 자동 적용 확인 | 2h | `SHOW TABLES;`에 `capture`가 있다. 앱 재기동해도 중복 실행 안 됨 |
| **T1.5** | `V2~V4` 상세 테이블 3개 + 엔티티 4개(`Capture`, `Expense`, `Todo`, `Link`) `@MapsId` 매핑 | 3h | 테스트에서 Capture+Expense 저장 후 조회가 된다 |
| **T1.6** | `POST /api/v1/captures` 구현 — **파싱 없이** 무조건 TODO로 저장. 요청 검증(빈 문자열, 500자 초과) | 3h | 201 응답 + DB에 capture/todo 행 생성 |
| **T1.7** | `@SpringBootTest` 통합테스트 1개 (POST → DB 확인), 테스트용 DB 설정 | 2h | `./gradlew test` 통과 |
| **T1.8** | 앱도 컨테이너로: `Dockerfile`(멀티스테이지 빌드) + compose에 `api` 서비스 추가, `.env.example` 작성 | 3h | **`docker compose up` 하나로 앱+DB가 뜬다** |

> **T1.8이 1주차의 진짜 산이다.** 여기서 막히는 전형적인 지점 세 가지를 미리 적어둔다:
> ① 앱이 `localhost:3306`을 찾는다 → 컨테이너 안에서 DB 주소는 `db:3306`(서비스 이름)이다.
> ② DB가 아직 준비 안 됐는데 앱이 먼저 뜬다 → compose `healthcheck` + `depends_on: condition: service_healthy`.
> ③ 빌드가 매번 느리다 → 멀티스테이지에서 의존성 다운로드 레이어를 소스 복사보다 **위에** 둔다.

## 2주차 — 파서

**이번 주 목표:** `"점심 9000원"`이 진짜로 지출로 저장된다.
**이번 주 데모:** 세 가지 예시 입력이 각각 다른 타입으로 저장되고, 파서 테스트 30개가 통과한다.

| # | 작업 | 예상 | 완료 기준 |
|---|---|---|---|
| **T2.1** | `ParseRule` 인터페이스, `ParsedCapture` DTO, `CaptureParser`(룰 순차 시도 + fallback), `Clock` 빈 | 2h | 룰이 0개여도 fallback으로 TODO가 나온다 |
| **T2.2** | `LinkRule` + 테스트 | 2h | URL만 / URL+한글 / URL 없음 케이스 통과 |
| **T2.3** | `ExpenseRule` — 금액 패턴 4종(`원`,`만원`,`천원`,콤마) + `merchant` 추출 | 3h | 테스트 12케이스 통과 |
| **T2.4** | `TodoRule` 날짜 파싱 — 상대(`오늘/내일/모레`), 절대(`9/2`, `9월 2일`), 요일 | 3h | `Clock.fixed`로 고정한 시각 기준 테스트 통과 |
| **T2.5** | `TodoRule` 시각 파싱 — `3시`, `오후 3시`, `15시` + 기본값 규칙(날짜만→09:00, 시각만→오늘/내일) | 3h | 조합 케이스 8개 통과 |
| **T2.6** | 파서를 `POST /captures`에 연결, 타입별 상세 행 저장, `source=AUTO` | 3h | 세 예시 입력이 각각 EXPENSE/TODO/LINK로 저장 |
| **T2.7** | `POST /captures/preview` (저장 없이 파싱 결과만) + 파서 테스트 30개 채우기 | 2h | `./gradlew test` 초록, 케이스 30개 이상 |
| **T2.8** | `GET /captures` — 타입 필터 + 커서 페이징 + `JOIN FETCH` | 3h | `?type=EXPENSE&size=5`로 5건 + `nextCursor` 반환 |

> **T2.3~T2.5는 정규식과 씨름하는 구간이다.** 정규식을 한 번에 완벽하게 짜려 하지 말고
> **테스트를 먼저 하나 쓰고 → 통과시키고 → 케이스를 하나 더 추가**하는 순서로 간다.
> 이 프로젝트에서 TDD가 가장 자연스럽게 몸에 붙는 부분이 여기다.

## 위험 신호와 대응

| 신호 | 언제 | 대응 |
|---|---|---|
| 1주차 끝에 `docker compose up`이 안 된다 | ~9/1 | **2주차를 미루고 T1.8을 끝낸다.** 이게 안 되면 4주차 배포가 통째로 무너진다 |
| 2주차 끝에 파서 정확도가 체감상 형편없다 | ~9/8 | 정확도를 높이려 하지 말고 **T3.5(고치기 UI)를 앞당긴다.** 고치기 쉬우면 정확도는 덜 중요하다 |
| 3주차 끝에 화면이 하나 안 끝났다 | ~9/15 | **요약 화면(T3.8)을 잘라낸다.** 입력·목록만 있어도 매일 쓸 수 있다 |
| 4주차에 도메인·HTTPS에서 막힌다 | ~9/22 | **T4.6을 잘라내고 IP:포트로 쓴다.** 배포는 성공한 것이다. HTTPS는 5주차에 |

## 막히면 잘라낼 순서

완성이 최우선이므로, 시간이 부족하면 **아래 순서대로** 잘라낸다. 위에서부터 잘라야 앱이 덜 망가진다.

1. **T4.6 도메인 + HTTPS** → IP 직접 접속으로 대체
2. **T3.8 요약 화면** → 목록에서 지출 탭만 봐도 됨 (API는 남겨둠)
3. **T2.5 시각 파싱** → 날짜만 파싱하고 시각은 09:00 고정
4. **T3.3 무한스크롤** → 최근 50건만 표시, 페이징 없음
5. **T4.2 PWA** → 그냥 모바일 브라우저 북마크

**절대 자르지 않는 것:** T1.8(compose로 전체 기동), T2.7(파서 테스트), T4.5(배포), T4.8(README).
이 네 개가 "제대로 완성"의 정의다.

## 부록: 나중에 목록

작업 중 떠오른 아이디어를 여기 적고 **하던 태스크로 돌아간다.** 4주가 끝나면 v2 후보가 된다.

실제로 만들면서 나온 것들. 4주가 끝나면 v2 후보가 된다.

**파서 (실사용에서 걸린 것)**
- `9시 회의` — 오전/오후 없는 1~11시를 오후로 보는 규칙 때문에 21:00이 된다.
  spec.md §3의 `내일 3시` → 15:00 예시를 맞추려다 생긴 대가다. 2주 써보고 재검토
- `다음주 금요일` — `다음주`가 먼저 매칭돼 +7일이 되고 요일 정보는 버려진다
- `(https://a.com)` — `\S+`가 닫는 괄호까지 URL로 삼킨다. 붙여넣기를 시작하면 만난다
- 어제/그저께 날짜 파싱 → 지출의 `spent_at`에 반영 (stack.md §7이 미뤄둔 것)

**화면**
- 전체 탭에 상세가 없어 정보량이 빈약하다 (아래 §미결 참고)
- 500자를 넣으면 제목이 조용히 200자로 잘린다. 사용자에게 알리지 않는다
- 목록에 검색이 없다. 기록이 쌓이면 필요해질 것

**운영**
- 토큰 재발급이 수동이다 (`.env` 수정 + 재배포)

**미뤄도 되는 것 (지금 하면 스코프 초과)**
- 지출 카테고리 자동 추론
- 파서 정확도 통계 화면 (`SELECT source, COUNT(*)` 한 줄이면 나온다)

## 부록: 미결 (stack.md §7에서 "3주차에 판단"이라고 미뤄둔 것)

**~~목록 전체 조회에 상세를 내려줄 것인가.~~ → 반영 완료.**
3주차에 실제로 화면을 만들어보니 `전체` 탭이 원문만 보여줘서 **정보량이 눈에 띄게 빈약하다.**
지출 탭에서는 `9,000원 / 점심`이 보이는데 전체 탭에서는 `점심 9000원`(원문)만 보인다.
타입이 섞이면 fetch join을 한 번에 못 하는 게 이유였는데, capture를 한 페이지 가져온 뒤
그 id들로 상세를 타입별 3번 더 조회하면 **총 4쿼리로 고정**된다(N+1이 아니다).
→ **넣었다.** 쿼리 수는 `ListQueryCountTest`가 Hibernate 통계로 고정한다.
